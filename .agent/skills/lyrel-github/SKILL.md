# Lyrel GitHub 工作流

路径均相对仓库根。文案语言与项目边界遵循 `AGENTS.md`；工单命令和字段以 `docs/agents/issue-tracker.md` 为项目入口，分诊先读 `docs/agents/triage-labels.md`。

## 查询与授权

1. 需要 GitHub 状态时从当前仓库 remote 确认目标，用 `gh` 读取相关 issue/PR、正文、评论和关联关系；不因开始本地任务而查询所有工单。
2. issue 与 PR 共用编号空间，先识别类型；认证或网络错误不能当作编号不存在。依赖和工单数量以当次回读结果为准，不使用记忆中的旧状态。
3. 确认用户授权的目标与操作范围后才写入。提供编号或要求调研不等于允许新建、评论、认领、改标签、关闭、推送或合并；发布规格也不等于授权实现。

## 工单与分诊

1. 只在明确要求时创建 issue、规格或工单树；使用用户批准的正文和目标，不顺带修改父工单标题、状态或标签。
2. 按现有文档建立原生 parent/sub-issue 关系与 blocking edges。依赖接口使用 blocker 的数字数据库 id：`gh api repos/<owner>/<repo>/issues/<n> --jq .id`，不是 issue number 或 `node_id`；字段和降级表示见工单文档。
3. 分诊角色映射以标签文档为准，不创建第二套名称。就绪任务只计未关闭 blocker，并排除已经认领的任务。
4. 写入后回读正文、标签、parent、children、blocking edges 和图的无环性，核对规格覆盖；只报告本轮已验证的数量。
5. 只有工作达到约定验收且获准更新状态时才关闭工单，评论附实际证据；部分成功、缺前提或未验证不能写成完成。

## 分支与 PR

- 已授权实施的一次性长任务使用会话/集成分支并经 PR 交付；已授权提交的简单修复可在主分支完成。分支约定不能代替提交、推送或合并授权。
- 对 #279 的 `docs/file-preview-editing-design` 及后续功能分支，同步主线时将分支独有提交 rebase 到最新 `origin/main`，不反复双向 merge；共享分支改写前先协调。
- 更新已发布分支仅用 `--force-with-lease`；lease 拒绝先核对远端新提交，不能改为无条件 force。最终 PR squash 合入，不制造 merge-commit 气泡、不重写主分支；已合入旧分支不承载后续工作。
- 其他任务遵循其明确的分支策略，不从历史工单推广出改写任意分支的权限。使用当前环境提供的选择性提交机制，只提交本次任务拥有的改动。

## 完成与清理

- 本地任务以约定范围完成和相关验证为完成条件；只有用户授权 GitHub 交付时，才要求会话分支已合入主分支，或改动已推送且对应 CI 通过。
- 清理前核对资源归属、未提交内容和共享引用。只处理会话引入且在授权范围内的临时文件、分支和 worktree；保留主检出、既有分支、他人工作和必需构建资产。
- Docker 仅清理本会话拉取且无共享用途的镜像；WSL 仅清理本次冗余文件。虚拟磁盘收缩属于单独的维护操作，确认目标、作用域和授权后才执行，不作为普通完成步骤自动启动。
- GitHub 交付记录 PR、合入提交或已推送 HEAD、CI、工单证据及实际清理项；本地交付不伪造这些字段，也不为补齐清单而发布。
