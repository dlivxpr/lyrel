# Lyrel 多工单规格实施

路径均相对仓库根。根 `AGENTS.md` 定义工程约束；GitHub 操作与分支策略使用 `.agent/skills/lyrel-github/SKILL.md`，构建与实际运行使用 `.agent/skills/lyrel-development/SKILL.md`。

## 开始条件

- 用户已授权实现目标规格，而不只是调研、拆票或发布规划。
- 已读取真实父规格、子工单、评论和当前 blocker，明确验收边界、平台和 fixture 前提；不虚构编号或把记忆当作当前依赖图。
- 已核对工作树中的用户改动和集成基线，不能为取得干净环境重置现有工作。

## 执行

1. 把工单组织成依赖图，选取没有未关闭 blocker 且未被认领的就绪任务；不要把工单顺序当作固定线性步骤。
2. 为本次实施建立一个集成分支。主智能体先界定切片和共享接口；仅在任务确实独立且值得并行时委派，其余自行完成。
3. 委派实现时使用 fresh context、基于当前集成基线的独立 worktree/分支；当前工具若提供隔离工作树则使用其机制。传递规格与工单路径、任务边界、工程约束、依赖契约和可观察验收结果，不能假定继承根 `AGENTS.md`。
4. 使用工具实际提供的 agent：调研使用可用只读角色，代码使用可用实现角色；模型 role 不等于 agent 名。内置 `task` 遵循其工具契约；只有经 Lyrel CLI 启动可见外部智能体时才读 `skills/lyrel/SKILL.md` 与其 `references/delegation.md`。
5. 实现按 `tdd` Skill 处理消费者可见行为和不确定边界；构建、测试和格式化时机遵守当前委派工具约定。子任务交付前同步最新集成基线，记录变更、证据及未验证项，不能声称未运行的 red/green 已通过。
6. 集成负责人检查共享接口和完整改动，在本次分支策略与授权范围内整合。每次整合后重算就绪任务，及时处理结果，不反复轮询或无必要地照看子任务。
7. 对整个集成分支使用 `code-review`，修复问题并按开发 Skill 完成相关检查和真实运行。原生 UI、SSH、IME、打包验收不能被 CI/headless 结果替代。
8. 只有已获 PR 发布授权时，首个集成提交后才能开 draft PR；代码审查、验收和授权满足后再转为 ready。工单状态更新、合入和清理按 GitHub Skill 执行，不由实施过程自行扩大权限。

## 完成条件

每个规格项有可追溯实现与实际验收证据，没有以 stub、TODO、跳过前提或缩小测试冒充完成。GitHub 交付时记录 PR、提交、CI、工单闭环和清理结果；没有这类授权时交付本地实现与证据，不自动推送或关闭工单。
