只能看到字节的终端，无法区分提示符和输出，也无法判断命令是已完成还是已挂起。lyrel 的 shell 集成弥补了这一缺口：shell 会报告提示符的起始位置、提交了什么命令、命令的退出码，以及当前所在的目录。

**你无需安装它。** 它会在窗格的 shell 启动时自动注入；如果你在其他地方运行同一个 shell，它则不会介入。

<a id="which-shells"></a>
## 支持哪些 shell

| Shell | 注入方式 |
|---|---|
| **zsh** | 使用临时 `ZDOTDIR`，其中的文件先加载你的文件，再加载 lyrel 的文件。继承的 `ZDOTDIR`、配置 `env.ZDOTDIR` 和 `.zshenv` 设置的目录均保留为用户配置目录；启动期间继续使用集成重定向器，首个提示符前恢复用户目录。 |
| **bash** | 使用一个先加载你自己的配置文件的 rcfile。 |
| **fish** | 使用 `-C` 初始化命令。 |
| **PowerShell** | 使用经过编码的初始化命令，包装现有的 `prompt` 函数和 PSReadLine 的行读取器。 |
| **nushell** | 使用 `--config` 包装配置，其中的 `config.nu` 先加载你的配置，再添加 lyrel 的钩子。仅适用于本地窗格。 |
| **WSL** *（Windows）* | 使用相同的脚本引导初始化发行版的 shell。 |
| **远程窗格** | 通过 SSH 引导初始化 zsh、Bash、fish 或已探测的 PowerShell；没有远端 Nushell 引导。可在**设置 → SSH →** 某个配置文件 **→ 高级 → 会话 → Shell 集成**中切换。 |

集成启用后会设置 `LYREL_SHELL_INTEGRATION`，防止 shell 嵌套时重复注入。它不会将集成带入嵌套的 shell——[你自行启动的 shell](#shells-you-start-yourself) 不会获得集成。

<Note>
  如果启动 shell 时使用了*你自己*填写的参数——`shell.args` 或 `custom_shells` 条目中的参数——lyrel 不会干预，因为注入会与你选择的标志冲突。lyrel 自身检测提供的参数（Git Bash 的 `-i -l`、WSL 条目的 `--distribution`）不在此列，因此这些条目仍会启用集成。
</Note>

Bash 4.4 及以上仍通过公开的 `PS0` 报告命令开始，保留用户 `PS0`；命令环境在父 shell 的链式 `DEBUG` action 中应用，不能在 `PS0` 的 command substitution 中修改父进程。Bash 3.2 使用同一环境生命周期和既有 `DEBUG` 兼容路径。用户 `DEBUG` action 仍先执行，保留其状态／跳过语义；若已安装 bash-preexec，则只接入其公开函数数组，不安装或下载它。`PROMPT_COMMAND` 的 scalar／array、历史设置、命令状态与提示符标记继续沿用原契约。

链式 `DEBUG` 尾调用将用户 action 执行后的 `$_` 保留为最后一个参数：Bash 会恢复 trap 前的 `$?`（4.4+ 还恢复 `PIPESTATUS`），但不会替集成恢复 `$_`。因此在 `: LAST_ARGUMENT` → 提示符边界的 `for` → 用户 prompt hook 序列中，内部 `BASH_COMMAND` 不会覆盖用户最后一个参数。没有用户 trap 时使用不改写 `$_` 的 compound conditional，而不是会清空它的裸 `:`；Bash 3.2 和 PS0 路径使用相同规则。Bash 3.2 原生 `DEBUG` 对 `PIPESTATUS` 的限制保持既有兼容边界，不伪造 pipeline 状态。

## 智能体的命令作用域环境

集成的 zsh、Bash、fish、PowerShell 识别直接输入的 `omp`、`kimi`、`pi`、`opencode`、`opencode2`、`hermes`，包括字面量参数、前置环境赋值和带引号的绝对路径。只对该次启动设置 `TERM_PROGRAM=kitty`、清空 `TERM_PROGRAM_VERSION`，并用 `LC_TERMINAL=lyrel`、`LC_TERMINAL_VERSION=$LYREL` 保留真实来源；远端未提供 `LYREL` 时使用构建该引导脚本的 lyrel 版本，不改 `TERM`。omp 另加 `PI_NO_DECCARA=1`。Hermes 0.23.1 的公开检测器不读取 `TERM_PROGRAM`，因此只给 Hermes 默认 `KITTY_WINDOW_ID=lyrel`，不覆盖显式 marker（包括空串），也不强制 `image.render`。

下一提示符恢复之前的已设置／未设置／空值以及 export 属性；成功、失败、Ctrl+C 和受支持的后台启动使用相同生命周期。PowerShell 的字面量 `$env:KEY='value'; omp ...` 属于该 shell 的前置赋值形式，七个终端／inline-config 字段在提示符前恢复。Windows PowerShell 5.1 和 Windows 上的 pwsh 7.5 之前版本会把 `Env:` 空赋值及 .NET setter 的空值当作删除；只有已识别的直接 agent 启动中、这七个字段的显式空字面量赋值才在实际执行文本中改用系统 setter，保留赋值顺序、显式身份优先级、原始历史／OSC 文本和 argv。pwsh 7.5+ 保留原生空赋值。未设置的字段始终通过 `Env:` provider 删除，避免 PowerShell 7.5+ 将传给 .NET setter 的 `$null` 转成空字符串；显式空值与非空值分别原样恢复。其他命令、字段及复杂表达式不改写；受限语言模式不能使用系统 setter 时会明确失败，不声称已保留空值。

显式命令级 `TERM_PROGRAM`／版本优先。`PI_IMAGE_PROTOCOL`、`PI_FORCE_IMAGE_PROTOCOL`、placeholder-off、agent 自身 graphics／inline-images 设置均不被开启或改写。`OPENCODE_CLI_CONFIG_CONTENT` 不生成、不合并、不进入持久化 scope；既有 inline 配置原样保留。

识别器不把 pipeline、compound command、substitution 或任意 interpreter 当作简单启动。Bash 只有完整提交的历史文本与当前 simple command 对应时才介入；关闭历史或被 `HISTIGNORE`／`ignorespace` 隐藏的输入保守回退，不修改历史配置。使用下方显式作用域语法处理这些形式。

PowerShell 5.1 不支持末尾 `&` 后台运算符；应使用 `Start-Job`／`Wait-Job`，并在 job 内显式提供目标 agent 的命令作用域（任意 scriptblock 不会被自动识别为直接启动）。真实 PTY 消费者通过生产 launch encoder 生成 job 内的局部环境，并检查 job 内恢复及父提示符不泄漏；pwsh 7 另外保留直接 `omp ... &` 的自动 scope 与下一提示符恢复检查。旧日志中的 `AmpersandNotAllowed` 是解析失败，不是有效后台启动证据。

本地 Nushell 不从没有命令文本的 `pre_execution` 猜测启动，而为六个正式名称定义小型 `def --wrapped`，用 `with-env` 调用相同名称的外部程序。参数保持为列表，`^` 保留外部 executable/PATH resolution；没有 PATH shim 或替代 binary。绝对路径、`^omp`、用户自己的同名命令／alias 或复杂 wrapper 应使用显式 `with-env`；不声称远端 Nushell 自动集成。

快捷启动、`agent_launch`、明确 `agent_commands` 映射、恢复／分叉与待连接窗格都通过已知 agent 的 launch preparation 带入相同 defaults，保留所选 Host／shell 和显式非敏感 selector。待连接窗格单独保留 agent 意图；Hermes 的缺省 marker 在目标 shell 执行时才补入，因此已有的非空／空 marker 都不被客户端覆盖。不解析 wrapper 脚本内容，也不扩大凭据 scope。自定义启动命令应为字面量 executable 与 argv（wrapper 可以是任意用户脚本）；需要 shell expression 的启动会显示不支持的原因，而不是猜测重放语义。

### 没有自动集成时的显式回退

嵌套 shell、不支持的 shell、关闭集成、使用自定义 shell args、手动 wrapper 或保守拒绝的命令形式不会自动变成 Kitty。只给目标 agent 一个局部环境，例如：

```bash
TERM_PROGRAM=kitty TERM_PROGRAM_VERSION='' LC_TERMINAL=lyrel LC_TERMINAL_VERSION="$LYREL" PI_NO_DECCARA=1 omp
```

PowerShell 可在新的子 shell 中设置环境，父提示符不受影响（使用实际安装的 `pwsh` 或 `powershell`，不要把 POSIX prefix 直接粘贴到 PowerShell）：

```powershell
pwsh -NoProfile -Command '$env:TERM_PROGRAM="kitty"; $env:TERM_PROGRAM_VERSION=$null; $env:LC_TERMINAL="lyrel"; $env:LC_TERMINAL_VERSION=$env:LYREL; $env:PI_NO_DECCARA="1"; & omp'
```

Nushell 使用原生作用域，不使用 `KEY=value`：

```nu
with-env {TERM_PROGRAM: kitty, TERM_PROGRAM_VERSION: '', LC_TERMINAL: lyrel, LC_TERMINAL_VERSION: $env.LYREL, PI_NO_DECCARA: '1'} { ^omp }
```

其他 agent 去掉 omp 专属 `PI_NO_DECCARA`；Hermes 可在该命令环境中加入 `KITTY_WINDOW_ID=lyrel`。保留自己的协议禁用参数；不要为兼容而设置全局 `TERM_PROGRAM=kitty`、更改 `TERM` 或添加 PATH shim。

<a id="what-it-reports"></a>
## 它会报告什么

| 信号 | 序列 | 用途 |
|---|---|---|
| 提示符开始 / 输入开始 | `OSC 133;A`、`133;B` | [提示符层](/terminal/prompt)：建议、补全、多行编辑 |
| 命令已提交 | `OSC 133;C` | 判断命令正在运行；在 ConPTY 不提供前台进程组信息的 Windows 上检测智能体 |
| 命令已完成，并附带退出码 | `OSC 133;D` | “耗时 42 秒后完成”通知、[历史记录](/terminal/history)中的失败标记 |
| 工作目录 | `OSC 7` | 让新标签页和拆分窗格在正确的位置打开、侧边栏的仓库分组、git 分支显示 |
| 编辑模式（vi / emacs） | `OSC 133;V` | 让 lyrel 的按键处理与你的 shell 模式保持一致 |
| 窗口标题 | `OSC 0` | 标签页标题。仅为 PowerShell 设置这一项——zsh、bash 和 fish 已经会自行设置标题，lyrel 会读取它们输出的标题 |

lyrel 注入的命令开始／结束标记带有 `;aid=lyrel` 归属属性，例如
`OSC 133;C;omp;aid=lyrel` 与 `OSC 133;D;0;aid=lyrel`。
只有这些边界能更新 Windows 的 shell 命令识别依据；TUI 自己发出或恢复历史输出时重放的
通用 `OSC 133` 输出块不清除仍在运行的 agent 图标。此属性用于区分协议来源，不是安全认证。
更新后新建 shell 窗格才会加载新的注入脚本；已运行的 shell 不会被自动改写或重启。

daemon 的前台事实由 `crates/lyrel-core/src/daemon/pane/facts.rs` 中的私有 `PaneFacts`
维护；`facts/output_marks.rs` 解释 shell／agent 标记、目录和标题，`facts/reader.rs`
持有单一输出流的解析状态与采样节奏，`facts/probes.rs` 负责平台进程观察。
PTY 与 native SSH 输出都沿同一顺序进入事实转换；窗格客户端接收有序状态帧，机器客户端
读取变化后的事实。事实仍使用原来的 pane-state 锁，不为采样另建锁或异步输出消费者；
机器事实只在释放该锁后发布。shell 启动注入和有界回放仍由原有 `launch`、`replay` 模块负责。
输出中的 OSC 标题和目录只解析一次，在 pane 状态中落地后才向客户端广播这批原始输出；
收到随后的完成标记后，立即查询窗格列表可见同批标题和目录，不需要等待额外轮询。
机器树通知、前台运行状态以及周期／提示符触发的 agent、远端上下文和目录探测均在输出广播后执行，
不会让这批字节等待这些慢路径。解析前仍保留图片接收所需的 Host locality 检查；shell／agent 标记
仍经前台提示符抑制和原有远端历史作用域规则应用，不因提前发布标题／目录而绕过。
`osc_title` 与实时探测的前台进程 `title` 分开维护，OSC 更新不会替换前台进程元数据。
没有 OSC 标题／目录更新的普通输出跳过提前落地所用的 pane-state 锁、事实应用和机器树发布；
标题重置 `Some("")` 仍按真实更新处理。输出后的既有事实观察路径保持不变。

近端 shell、嵌套程序和远端提示符不是同一事实：前台程序转发的提示符不能启用近端编辑器，
但标记自身的提示符读数仍用于判断远端是否忙碌。每次切换远端上下文会清除旧目录和集成证明；
同一批输出里的新远端上下文先落地，随后才记录它的首个提示符。回到近端提示符时立即重新采样，
不等下一个轮询周期。间接图片文件／共享内存的许可仍需在接收边界重新证明 Host locality；
缓存的进程组或远端 UI 上下文都不能单独授予本地文件读取权限。

平台验证必须分别记录：macOS 的目录回退依赖 PTY 前台进程组与 `proc_pidinfo`，
Linux 依赖可读取的 `/proc/<pid>/cwd` 和 argv；两者的真实 argv 场景需要 `bash` 与本机 PTY。
Windows ConPTY 没有相同的前台进程组／目录回退，agent 识别依赖带 `aid=lyrel` 的 shell
命令标记，标题回退使用本机进程快照；Windows 绿灯不证明 Unix probe 已验证。
真实 native SSH 与嵌套 SSH 的 locality 场景还需要隔离远端主机、已核验 Host key 和对应 shell，
不得用本机路径或普通标记 fixture 代替远端运行证据。

<a id="what-turns-off-without-it"></a>
## 没有集成时哪些功能会受影响

运行 lyrel 未集成的 shell 时，以下所有功能仍然可用，只是会退回到精度较低的信息来源：

- 灰字建议、补全菜单，以及 <kbd>⌃ R</kbd> 的模糊历史记录搜索
- “命令已完成”通知和历史记录搜索中的失败标记
- 精确的工作目录跟踪

窗格、拆分、回滚缓冲区、搜索、SSH 和 CLI 不受影响。

工作目录的回退机制值得详细了解，因为它并非在所有环境中都可用。在 lyrel 能查看窗格进程的环境中，它会改为读取前台进程自身的工作目录——包括 macOS 或 Linux 上的本地窗格，以及远程工作区中的窗格，后者由该主机上的 `lyrel-server` 负责读取。这是轮询，而非主动报告：仅在窗格产生输出时采样，每秒最多两次，因此执行 `cd` 后，目录显示可能要等到窗格再次输出内容才会更新。**Windows** 上的本地窗格和连接到 **SSH 主机**的窗格完全没有回退机制——无法读取 `ssh` 另一端的进程表，因此，如果 shell 不报告目录，窗格就会继续显示上一次收到报告的目录。

<a id="shells-you-start-yourself"></a>
## 你自行启动的 shell

注入发生在窗格的 shell *启动时*。在 bash 提示符下输入 `zsh`——或 `bash`、`sh`、`docker exec … sh`——第二个 shell 就是一个新进程，由你的 shell 而非 lyrel 启动。它不会发出提示符标记，也不会发出 `OSC 7`，窗格会继续显示外层 shell 最后报告的目录，直到你退出并返回外层 shell。

在你自己的机器上，这通常不会显现出来，因为提示符框架会自行报告目录：oh-my-zsh 通过 `lib/termsupport.zsh` 中的 `omz_termsupport_cwd` 完成这一工作。**通过 SSH 时则不一样。** 当设置了 `SSH_CLIENT` 或 `SSH_TTY` 时，该文件会提前返回，因此在远程主机上，你手动启动的 zsh 完全不会报告目录，lyrel 也无法代为报告。

要让该 shell 获得集成，请将它设为 lyrel 启动的 shell：

- **远程主机。** lyrel 连接时会向主机查询 `$SHELL`，并引导初始化该 shell，因此应使用 `chsh -s /bin/zsh` 切换，然后重新连接。在**高级 → 会话**下设置运行 `zsh` 的登录脚本*不能*实现这一点——这些行是在 shell 已经启动后输入会话的，因此与其他手动启动方式一样，只会形成嵌套。在 `.bashrc` 中执行 `exec zsh` 也不行：它会替换 lyrel 已配置好的进程。
- **本地窗格。** 设置**设置 → 终端 → Shell → 程序**（或[配置](/reference/configuration)中的 `shell`），并将**参数**留空——你填写的参数会关闭注入。

<a id="per-pane-history"></a>
## 每个窗格独立的历史记录

启用 `per_pane_history` 后，这一功能也依赖集成才能工作。集成在你自己的 rc 文件*之后*运行——也正因如此，它才能实现这一功能：`$HISTFILE` 由你设置，可以指向任意位置，在此之前，shell 外部无法知道它指向哪里。

具体顺序是：先用你的实际历史记录填充窗格的私有文件，避免从空白开始；记录填充了多少内容；重新设置 `$HISTFILE` 的指向；最后在窗格关闭时，将该标记之后的全部内容合并回去。

<a id="remote-shells"></a>
## 远程 shell

对于远程工作区或 SSH 窗格，相同的脚本会在登录时通过连接发送，因此远程窗格会像本地窗格一样报告工作目录、退出码和提示符标记。要针对特定主机关闭此功能，请前往该配置文件的**高级 → 会话**。
