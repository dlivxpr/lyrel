**Settings → About** 显示当前版本，并提供检查及安装更新的入口。
**Settings → General → Updates** 保留自动检查、后台下载和代理设置。
<a id="channels"></a>
更新仅使用 stable 发布，不再提供渠道切换。

lyrel 的独立初版版本／标签为 `0.1.0`／`v0.1.0`，发行源仅为
[`dlivxpr/lyrel`](https://github.com/dlivxpr/lyrel/releases)。可用平台资产以对应版本页面为准；
缺少 lyrel 发布包时，不会回退到上游下载，也不能据本地 fixture 声称在线更新成功。

<a id="how-it-works"></a>
## 检查、下载与安装

<Steps>
  <Step title="检查稳定发布">
    应用启动时及之后每六小时检查一次。设置 `check_for_updates: false` 可以关闭自动检查；
    **Check now** 仍可手动检查。

    更新器分页读取本项目的 `/releases` 列表，跳过草稿、预发布、非桌面发布及桌面包
    版本与标签不匹配的发布，再按 SemVer 选择最高稳定版本，而非依赖发布时间或
    GitHub 手动选择的 latest。支持 `0.1.0` 与 `v0.1.0`；只有比当前版本更新的
    stable 才会提示更新，相同版本（包括仅 build metadata 不同）和旧版本不会触发升级。
  </Step>
  <Step title="后台下载并校验">
    `auto_download_updates` 默认为 `true`。应用只选择精确匹配当前平台、架构和安装形态的包，
    并使用 `checksums.txt` 校验完整性。缺少匹配包或校验和时，不会猜选其他包或跳过验证，
    而是说明原因并保留发布页入口。

    下载完成不等于同意安装。已校验的包会等待用户选择；按流量计费时可以关闭后台下载。
    包大小以实际发布资产为准，尚未发布的 lyrel 包不提供推测下载体积。
  </Step>
  <Step title="安装并重新启动">
    用户选择安装后，专用 `lyrel-updater` 会检查包版本及安装布局；macOS 还检查代码签名要求。
    失败信息会保留，重新启动失败时恢复原有安装。用户可以丢弃暂存包或取消下载。

    “稍后”只推迟提示，不会永久忽略该版本。下次启动时安装也需要用户明确选择；需要提升
    权限的安装不能作为无人值守的下次启动更新。
  </Step>
</Steps>

<a id="platform-notes"></a>
## 平台限制

<AccordionGroup>
  <Accordion title="macOS">
    自动更新要求可安全替换的应用包和可写目录。不满足条件时，通过发布页手动安装。
    更新器在原安装路径替换整个 `.app`，不通过更换安装目录保留权限。

    **历史 ad-hoc 包不能提供跨升级的稳定签发者身份。** 即使 `CFBundleIdentifier`
    与签名 Identifier 不变，默认 designated requirement 中的 `cdhash` 也会随代码变化；
    隔离签名验证已确认，两份不同二进制使用同一 Identifier 做 ad-hoc 签名后，后者不能满足
    前者的 requirement。这是权限无法稳定延续的已确认身份条件缺口，不是已完成的 TCC
    跨升级重授权实验。没有读取或修改 TCC 数据库，也没有借测试申请实际权限。

    正式发布现在要求同一 Apple Developer Team 的 **Developer ID Application** 签名、
    固定 bundle ID `io.github.dlivxpr.lyrel` 和已附加的公证票据。缺少签名／公证凭据时
    发布失败，不再静默回退到 ad-hoc；复用旧 run 的 ZIP 与 DMG 同样经过签名身份门控。
    同 Team、同 Identifier 的合法证书签名提供跨代码版本验证的身份条件，而不是把
    requirement 放宽为任何人都能仿冒的 bundle ID。

    **从历史 ad-hoc 迁移到 Developer ID 需要手动安装完整新包一次，并重新授予所需权限。**
    旧授权不能安全地自动迁移到新的签发者身份。更新器不自动跨越两种签名姿态：ad-hoc
    安装仅接受同 Identifier 的 ad-hoc 更新，仍校验官方归档 SHA-256、预期版本及完整签名；
    证书签名安装要求新包实际满足当前安装的 requirement，不接受降级为 ad-hoc。
    本地无证书构建仍可使用 ad-hoc，但不能承诺升级保留权限。不要通过删除签名、重置 TCC
    或关闭系统安全功能规避身份检查。

    签名身份连续不等于所有权限永不再询问；macOS 版本、具体权限策略、签发 Team 或
    bundle ID 变化仍可能要求授权。公证用于发行安全检查，不授予辅助功能、完全磁盘访问等
    用户权限。本项目尚未完成真实 Developer ID 两版本安装与 TCC 保留的端到端验收。

    若旧版本内置 updater 已报 `codesign did not report a designated requirement`，
    需从本项目发布页手动安装包含修复的完整新包一次；修改源码不会替换已安装的旧 helper。
    不要删除签名、绕过 checksum 或只替换单个可执行文件。requirement 与 ad-hoc 的差异见
    [Apple TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements)。
    新 GUI 在协议兼容时复用本地 server，使 shell 在更新后继续运行；协议不兼容时，
    明确询问用户保留还是重启 server。
  </Accordion>
  <Accordion title="Windows">
    自动更新识别 Inno Setup 与便携 ZIP 安装的标记、updater 和目录权限。
    `.lyrel-inno-install` 必须为 `inno-v1`，`.lyrel-portable` 必须为 `portable-v1`；
    同时存在或内容无效时拒绝自动安装，不猜测安装形态。安装器使用独立 AppId
    `{E57DD2B4-E65D-4F13-9E2E-8D929125780A}`，不识别旧产品的安装注册。
    Windows 不能替换正在运行的 daemon 镜像，因此更新会先停止本产品服务，并在用户确认前说明影响。
    所有用户安装可能要求 UAC 提权；无法安全识别或替换的布局保留手动安装入口。
    便携 ZIP 必须包含固定版本、匹配架构的 `conpty.dll`、`OpenConsole.exe` 和
    `LICENSE-ConPTY.txt`；updater 在移动原安装文件前校验三者摘要。缺失或不匹配时
    拒绝安装，请重新下载匹配的完整发行包，不要用系统宿主或其他版本文件补齐。
  </Accordion>
</AccordionGroup>

暂存、替换、备份恢复和清理仅使用 lyrel 自有安装及资源。便携更新保留 `data/`；
中断替换的 lyrel 备份不会被当成成功更新清除。其他产品的安装、标记、暂存及数据不参与扫描或恢复。

## 发行资产与验证前提

桌面包、精确平台／架构后缀、WSL server 布局及手动构建入口见
[安装与手动打包](/getting-started/installation#在专用工作树中手动打包)。每次 stable
发行使用统一版本，并附带 `checksums.txt`，其中每行是 SHA-256 和裸资产文件名。
macOS 更新选择 ZIP，Windows 按安装形态选择 Setup 或便携 ZIP；不提供 Linux 桌面包或 AppImage 更新。Linux 远端 server 的安装与校验、Windows 随包 WSL server 不受影响。
缺少精确包、checksum 条目或校验失败时不会执行替换。

### macOS 正式发布的签名与公证前提

维护者需要自行持有有效的 Apple Developer 会员资格、该 Team 的 Developer ID Application
证书与私钥，并在仓库 Actions secrets 配置：

- `APPLE_CERTIFICATE`：包含私钥的 `.p12` 文件的 Base64；加密文件还需
  `APPLE_CERTIFICATE_PASSWORD`。不要把证书、私钥或密码提交到仓库。
- `APPLE_SIGNING_IDENTITY`：实际 Developer ID Application 签名身份，不能为 `-`。
- `APPLE_TEAM_ID`：预期的 10 位 Team ID；发布门控验证签名证书中的 Team，不只比较名称。
- 公证凭据二选一：完整的 `ASC_KEY_P8`、`ASC_KEY_ID`、`ASC_ISSUER_ID`；或
  `APPLE_ID` 与 `APPLE_PASSWORD`（App 专用密码，结合上述 `APPLE_TEAM_ID`）。

这些凭据不能由构建脚本自动替维护者申请。未配置时，正式发布被阻止；不能把当前源码
变化解释为已经具备证书或已经完成公证。以后更新继续使用同一 Team 和 bundle ID；更换
Team 不是普通证书续期，需要单独评估身份迁移和用户授权。

`.github/scripts/bundle-macos.sh` 的本地调用默认保留原有开发签名方式；正式工作流设置
`LYREL_REQUIRE_RELEASE_SIGNING=1`，并在打包后验证 Apple Developer ID Application
证书链、Team、bundle ID、随包可执行文件签名及附加的公证票据。发布汇总前再次检查
ZIP 和只读挂载的 DMG，旧资产不会因为曾经构建成功而豁免。


发布列表／资产选择 fixture 与 updater 测试只能证明确定性契约。真正在线更新需要本项目
已发布且非 draft／prerelease 的新版本、相应平台包和真实校验和；平台安装、UAC、macOS
签名／公证和失败恢复需在授权的隔离环境分别验收。当前没有这些在线发行前提，不能宣称
Windows、macOS 均已完成安装或更新；Linux 仅保留 server／CLI，不纳入桌面更新验收。

<a id="the-background-server-is-still-running-build"></a>
## 后台 server 仍在运行旧版本

GUI 更新后，窗格可能仍由此前启动的 server 提供服务。设置会显示其 build。
重启 server 会结束窗格中的进程，包括 shell、agent 和 SSH 会话；请在工作空闲时主动选择。

<a id="proxies"></a>
## 代理

更新检查及下载依次解析以下代理来源：

1. `config.json` 的 `http_proxy`，例如 `http://127.0.0.1:7890` 或 `socks5://127.0.0.1:1080`。
2. 平台系统代理（Windows registry、macOS `SCDynamicStore`）。
3. `HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY`。

窗格内运行的程序不受该配置影响，它们仍使用自己的环境变量。
