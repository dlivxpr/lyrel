打开「设置 → 关于」查看版本、手动检查或安装更新。「关于」页的「更新」分组可设置自动检查、后台下载和应用 HTTP 代理。
<a id="channels"></a>
更新仅使用 stable 发布，不再提供渠道切换。

lyrel 的独立初版版本／标签为 `0.1.0`／`v0.1.0`，发行源仅为
[`dlivxpr/lyrel`](https://github.com/dlivxpr/lyrel/releases)。可用平台资产以对应版本页面为准；
缺少 lyrel 发布包时，不会回退到上游下载，也不能据本地 fixture 声称在线更新成功。

<a id="how-it-works"></a>
## 检查、下载与安装

<Steps>
  <Step title="检查稳定发布">
    应用启动时及之后每六小时检查一次。设置 `check_for_updates: false` 可以关闭自动检查；
    **Check now** 仍可手动检查。

    更新器分页读取本项目的 `/releases` 列表，跳过草稿、预发布、非桌面发布及桌面包
    版本与标签不匹配的发布，再按 SemVer 选择最高稳定版本，而非依赖发布时间或
    GitHub 手动选择的 latest。支持 `0.1.0` 与 `v0.1.0`；只有比当前版本更新的
    stable 才会提示更新，相同版本（包括仅 build metadata 不同）和旧版本不会触发升级。
  </Step>
  <Step title="后台下载并校验">
    `auto_download_updates` 默认为 `true`。应用只选择精确匹配当前平台、架构和安装形态的包，
    并使用 `checksums.txt` 校验完整性。缺少匹配包或校验和时，不会猜选其他包或跳过验证，
    而是说明原因并保留发布页入口。

    下载完成不等于同意安装。已校验的包会等待用户选择；按流量计费时可以关闭后台下载。
    包大小以实际发布资产为准，尚未发布的 lyrel 包不提供推测下载体积。
  </Step>
  <Step title="安装并重新启动">
    用户选择安装后，专用 `lyrel-updater` 会检查包版本及安装布局；macOS 还检查代码签名要求。
    失败信息会保留，重新启动失败时恢复原有安装。用户可以丢弃暂存包或取消下载。

    “稍后”只推迟提示，不会永久忽略该版本。下次启动时安装也需要用户明确选择；需要提升
    权限的安装不能作为无人值守的下次启动更新。
  </Step>
</Steps>

<a id="platform-notes"></a>
## 平台限制

<AccordionGroup>
  <Accordion title="macOS">
    自动更新要求可安全替换的应用包和可写目录。不满足条件时，通过发布页手动安装。
    更新器在原安装路径替换整个 `.app`，不通过更换安装目录保留权限。

    **当前 ad-hoc 包不能提供跨升级的稳定签发者身份。** 即使 `CFBundleIdentifier`
    与签名 Identifier 不变，默认 designated requirement 中的 `cdhash` 也会随代码变化；
    隔离签名验证已确认，两份不同二进制使用同一 Identifier 做 ad-hoc 签名后，后者不能满足
    前者的 requirement。这是权限无法稳定延续的已确认身份条件缺口，不是已完成的 TCC
    跨升级重授权实验。没有读取或修改 TCC 数据库，也没有借测试申请实际权限。

    本阶段正式发布继续使用固定 bundle ID `io.github.dlivxpr.lyrel` 的 ad-hoc 包，
    不要求 Developer ID 或 Apple 公证；没有配置 Apple 凭据也允许发行。保留架构、完整
    代码签名、官方归档 SHA-256、预期版本及下载来源校验，不以签名姿态放宽这些边界。

    **升级后仍可能需要重新授予系统权限，本版本没有解决权限延续问题。** 若以后迁移到
    同 Team、同 Identifier 的 Developer ID 签名，需要手动安装完整新包一次，并重新授权。
    更新器不自动跨越两种签名姿态：ad-hoc 安装仅接受同 Identifier 的 ad-hoc 更新；
    证书签名安装要求新包实际满足当前安装的 requirement，不接受降级为 ad-hoc。
    不要通过删除签名、重置 TCC 或关闭系统安全功能规避身份检查。

    签名身份连续不等于所有权限永不再询问；macOS 版本、具体权限策略、签发 Team 或
    bundle ID 变化仍可能要求授权。公证用于发行安全检查，不授予辅助功能、完全磁盘访问等
    用户权限。本项目尚未完成真实 Developer ID 两版本安装与 TCC 保留的端到端验收。

    若旧版本内置 updater 已报 `codesign did not report a designated requirement`，
    需从本项目发布页手动安装包含修复的完整新包一次；修改源码不会替换已安装的旧 helper。
    不要删除签名、绕过 checksum 或只替换单个可执行文件。requirement 与 ad-hoc 的差异见
    [Apple TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements)。
    新 GUI 在协议兼容时复用本地 server，使 shell 在更新后继续运行；协议不兼容时，
    明确询问用户保留还是重启 server。
  </Accordion>
  <Accordion title="Windows">
    自动更新识别 Inno Setup 与便携 ZIP 安装的标记、updater 和目录权限。
    `.lyrel-inno-install` 必须为 `inno-v1`，`.lyrel-portable` 必须为 `portable-v1`；
    同时存在或内容无效时拒绝自动安装，不猜测安装形态。安装器使用独立 AppId
    `{E57DD2B4-E65D-4F13-9E2E-8D929125780A}`，不识别旧产品的安装注册。
    Windows 不能替换正在运行的 daemon 镜像，因此更新会先停止本产品服务，并在用户确认前说明影响。
    所有用户安装可能要求 UAC 提权；无法安全识别或替换的布局保留手动安装入口。
    便携 ZIP 必须包含固定版本、匹配架构的 `conpty.dll`、`OpenConsole.exe` 和
    `LICENSE-ConPTY.txt`；updater 在移动原安装文件前校验三者摘要。缺失或不匹配时
    拒绝安装，请重新下载匹配的完整发行包，不要用系统宿主或其他版本文件补齐。

    便携包最多包含 4096 个 ZIP 条目；目录元数据、每个条目的压缩与展开大小，以及
    所有条目累计展开大小均不得超过 1 GiB。更新器在解析完整目录前核对声明和实际
    目录记录的资源边界，也检查 ZIP64 元数据；伪造较小的目录条目数不能绕过限制。
    SHA-256、读取至 EOF 的 CRC32／大小校验、UTF-8 名称、规范路径、符号链接与
    重复路径检查仍保留。拒绝发生在停止 daemon 和移动原安装文件之前。
    这些限制不改变下载方式：更新器仍会将整个 ZIP 读入内存。
  </Accordion>
</AccordionGroup>

暂存、替换、备份恢复和清理仅使用 lyrel 自有安装及资源。便携更新保留 `data/`；
中断替换的 lyrel 备份不会被当成成功更新清除。其他产品的安装、标记、暂存及数据不参与扫描或恢复。

## 发行资产与验证前提

桌面包、精确平台／架构后缀、WSL server 布局及手动构建入口见
[安装与手动打包](/getting-started/installation#在专用工作树中手动打包)。每次 stable
发行使用统一版本，并附带 `checksums.txt`，其中每行是 SHA-256 和裸资产文件名。
macOS 更新选择 ZIP，Windows 按安装形态选择 Setup 或便携 ZIP；不提供 Linux 桌面包或 AppImage 更新。Linux 远端 server 的安装与校验、Windows 随包 WSL server 不受影响。
缺少精确包、checksum 条目或校验失败时不会执行替换。

### macOS 签名与公证状态

当前 macOS 正式包使用 ad-hoc 签名，未经 Developer ID 签名或 Apple 公证；Windows 包
也未进行发行者签名。ad-hoc 仅满足代码完整性和 Apple Silicon 执行要求，不提供受信任的
发行者身份、不保证通过 Gatekeeper，也不能保证跨升级保留系统授权。

维护者以后可自行配置 `APPLE_CERTIFICATE`、`APPLE_CERTIFICATE_PASSWORD`、
`APPLE_SIGNING_IDENTITY` 和 `APPLE_TEAM_ID`，并提供完整的
`ASC_KEY_P8`／`ASC_KEY_ID`／`ASC_ISSUER_ID` 或 `APPLE_ID`／`APPLE_PASSWORD` 公证凭据。
打包脚本保留既有可选证书签名／公证路径，但这些凭据不是当前发布前提，脚本不会自动申请，
也不应将证书、私钥或密码提交到仓库。


发布列表／资产选择 fixture 与 updater 测试只能证明确定性契约。真正在线更新需要本项目
已发布且非 draft／prerelease 的新版本、相应平台包和真实校验和；平台安装、UAC、macOS
签名／公证和失败恢复需在授权的隔离环境分别验收。当前没有这些在线发行前提，不能宣称
Windows、macOS 均已完成安装或更新；Linux 仅保留 server／CLI，不纳入桌面更新验收。

### 用本地资产复测安装、更新和恢复

使用预留的桌面测试登录会话和来自两个已知提交的 Release 分发包，记为 `OLD` 和 `NEW`（`NEW` 的版本更高）。
保留每个版本生成的 `checksums.txt`，在首次执行包内程序前，按精确资产名独立比对 SHA-256。
Windows 的离线 ConPTY 准备命令为 `pwsh scripts/prepare-conpty.ps1 -Offline`，其余打包步骤见
[手动打包与验证](/getting-started/installation#在专用工作树中手动打包)。macOS 使用已经签名、签名要求匹配的本地包。

1. 每个样本创建独立的运行目录，准备 `config/`、`work/`、`tmp/` 和证据目录。GUI、updater 和 CLI
   共享绝对路径 `LYREL_CONFIG_DIR=<运行目录>/config`，避免连接日常 daemon。先写入 `config.json`，
   设置 `install_cli_on_path: false`、`check_for_updates: false`、`auto_download_updates: false`、
   `restore_session: true`、`show_tray_icon: false` 和 `notify_on_command_finish: "never"`。
   用无真实凭据或智能体配置的测试登录会话。Windows 在运行目录放置 `CACHEDIR.TAG`，触发启动时的开始菜单写入跳过逻辑。
   测试进程树的 `TEMP`、`TMP` 指向 `tmp/`，隔离旧暂存目录扫描。
2. 在 Windows 解包 `OLD` 的便携 ZIP 到运行目录下的空子目录。macOS 将 `OLD` 的 DMG 用 `hdiutil attach -readonly -nobrowse`
   挂载到私有目录，用 `ditto` 复制 `lyrel.app` 后卸载镜像。使用已安装副本的绝对路径启动 GUI。
   用包内 CLI 的 `lyrel --version` 及 Windows GUI/updater 的 PE `ProductVersion` 或 macOS 的
   `CFBundleShortVersionString` / `CFBundleVersion` 核对版本。
3. 用 `lyrel new --open <work> --json` 创建并显示夹具工作区，保存 `lyrel ws tree <id> --json`。
   保留这个工作区的窗口作为重开目标。在该窗格执行产生短唯一行的 shell 命令并记录目录和 shell PID（支持的 shell）。
   确认初始标记已显示并被 `lyrel capture %<pane> --plain --scrollback` 读到。
   恢复样本和更新样本分别从新的 `OLD` 副本及相同夹具内容开始。
4. 从 `OLD` 副本复制 updater 到私有暂存目录。`stage` 为预先创建的全新目录，macOS 上放在 `lyrel.app` 同卷的同级目录。
   通过下表的真实 helper 执行 `NEW` 预检，要求退出码为 `0`。`pid` 是夹具 GUI 的 PID。
   Windows 先启动安装 helper，再正常退出夹具 GUI，由 helper 等待 `pid`。macOS 从外部启动的 helper 不持有 GUI 的父子关系，
   所以先正常退出夹具 GUI 并确认其已退出，再执行安装命令。由 helper 自行重开窗口。
   给每阶段设定一致的超时。Windows 用进程句柄等待 GUI subsystem helper 的退出并读取退出码。
   日志和 outcome 放在 `stage` 外的证据目录，避免 updater 清理时移除。`asset` 为 `zip` 的裸文件名，`version` 为 `NEW` 的版本。
5. 恢复样本使用相同的成功预检。安装阶段将 `checksums` 替换为一份私有副本，仅把 `NEW` 对应条目的摘要改成错误值。
   期望 helper 重新校验失败并自行重开 `OLD`，退出码非零，outcome 的 `ok` 为 `false` 且 `detail` 指明摘要不匹配。
   更新成功样本应得到退出码 `0`、`ok: true` 和 `NEW`。这条恢复场景覆盖替换前拒绝后的重开。
6. 在自动重开的窗口中比对工作区、窗格布局、目录和此前的标记，再向当前窗格输入另一条命令，等待新的结果行显示。
   例如，Windows 可将夹具 shell 配置为 `{"program":"cmd.exe","args":["/D"]}`，并输入 `for %I in (OK) do @echo LYREL448_7621%I`。
   macOS 可输入 `printf '%s%s\n' LYREL448_7621 OK`。两者都核对完整的独立结果行 `LYREL448_7621OK`，排除输入回显。
   用 `ws tree` 重新解析窗格并留存 capture 作为补充证据。Windows 成功替换会停止 daemon，验收是原布局和历史恢复到一个新 shell。
   macOS 的兼容更新及替换前失败恢复应保留原有 shell。样本结束后关闭夹具 GUI，以同一配置执行 `lyrel server stop`，
   保留证据，并清理本次样本创建的目录。

下表参数按位置传递，路径含空格时作为单个参数。替换命令均追加 `--config-dir <config> --result-file <outcome.json>`。

| 平台 | 预检 | 替换 |
| --- | --- | --- |
| Windows 便携 | `lyrel-updater.exe verify-portable <zip> <checksums> <asset> <version> <stage>` | `lyrel-updater.exe install-portable <pid> <zip> <checksums> <asset> <install-dir> <version> <log> <stage>` |
| macOS | `lyrel-updater verify <lyrel.app> <zip> <checksums> <asset> <stage> <version>` | `lyrel-updater install <pid> <lyrel.app> <zip> <checksums> <asset> <stage> <version> <log>` |

计时点分别为开始验证／安装包、首次显示可用 shell、开始预检、启动替换 helper、helper 退出、重开窗口显示新命令的结果。
在同一预留硬件上交替运行基线和候选，记录各阶段时长、样本数、运行间波动，以及 GUI、daemon、updater 和相关子进程的 CPU 时间和内存峰值。
按需记录 GUI GPU 指标。保留两个版本的提交、资产摘要、实际命令、系统与硬件、安装版本、outcome 及窗口证据，分开记录构建和打包耗时。
该流程覆盖离线的便携安装和应用包复制。Inno 注册、权限提示、线上发布发现和替换后的回滚需另有对应场景和证据。

<a id="the-background-server-is-still-running-build"></a>
## 后台 server 仍在运行旧版本

GUI 更新后，窗格可能仍由此前启动的 server 提供服务。设置会显示其 build。
重启 server 会结束窗格中的进程，包括 shell、agent 和 SSH 会话；请在工作空闲时主动选择。

<a id="proxies"></a>
## 代理

更新检查及下载依次解析以下代理来源：

1. `config.json` 的 `http_proxy`，例如 `http://127.0.0.1:7890` 或 `socks5://127.0.0.1:1080`。
2. 平台系统代理（Windows registry、macOS `SCDynamicStore`）。
3. `HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY`。

窗格内运行的程序不受该配置影响，它们仍使用自己的环境变量。
